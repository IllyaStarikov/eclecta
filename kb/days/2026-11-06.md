### [sshole](https://sshhole.com/) — 8/10

On musl-based systems (Alpine) running sshd without PAM, pasting an overlong or malformed string into a password prompt can log you into an account that was deliberately locked with "*" in /etc/shadow, because crypt() failure and an intentionally locked account produce the exact same sentinel.

Notes: The root cause is one overloaded character: Bill Joy put '*' in 3BSD's /etc/passwd in 1980 as a hash that can never match (locking the 'daemon' account); musl later reused '*' for a second, unrelated meaning. · Since musl commit b3c4cc12 (Aug 2012), crypt() returns the single character '*' on failure instead of NULL, so programs that never checked for NULL stop crashing but now see a failed hash that is byte-identical to a locked-account field. · Twenty days later, commit 88bf5a8a capped sha512crypt input at 256 bytes (sha512crypt slows with password length, a DoS vector); anything longer makes crypt() fail and return '*'. So a wrong password over 256 bytes compared against a stored '*' matches. · The bypass only triggers on musl WITHOUT PAM: PAM never calls crypt() for a '*' field, and most distros go through PAM. A fresh box with no password set is not affected; a locked '*' account needs one wrong attempt first. · Prior incidents in the same code path: CVE-2016-6210 (sshd username timing oracle, fixed by hashing against a borrowed salt for nonexistent users, which also catches real '*' users) and CVE-2019-5021 (Alpine Docker images shipped with no root password; Alpine later switched root-lock from '!' to '*' in 3.16/2022 so ssh keys still work, re-exposing this path). · Author claims the bug was found by fuzzing ~17,600 logins across glibc/musl/pam/no-pam/shadow/no-shadow sshd builds (with 'agent swarms'); every build agreed except musl-without-PAM, which accepted logins it should have rejected. Found four days after an Oct 2026 OpenSSH security review patched pick_salt() but missed this bug four lines below. Severity, CVE assignment, and real-world exploitation are self-reported and unverified in the text.

### [Qwenputer: A functioning, deterministic RISC-V CPU inside Qwen3.5](https://divagr.com/blog/qwenputer) — 8/10

Notes: Mechanism: on Qwen3.5 4B, 3 of every 4 attention layers use Gated DeltaNet (a linear RNN). Setting the forget gate to 1 (no decay), write strength beta to 1 (full overwrite), and one-hot keys turns each GDN head's fixed-size state matrix into exact addressable RAM, cheaper than KV-cache-as-RAM because state size is constant regardless of context length. · No training: a compiler sets weights directly to encode a 32-bit RV32IM RISC-V core (plus Zba extension and a bignum unit), occupying 11 of Qwen's 32 layers. No external tool call or sandbox; instructions ride on the tool-call format via an RvChat driver. · An experimental in-weights filesystem hashes names into 1,024 directory slots in DeltaNet state, holds ~512 files (~53,000 tokens), and persists across conversations; changed-fact recall hit 90% vs 30% for pasting old chats. Code on the rv-store branch. · Caveats: checkpoint is 18.8 GB (roughly double base Qwen, mostly zero padding), runs on one 24 GB GPU, needs the RvChat driver (no plain generate() yet), and is slow, a few decoded tokens per instruction, ~3,200 CPU tokens/sec on an L4. Author flags safety follow-ups: hiding reasoning in RNN state to evade CoT monitoring, or using compiled weights as a monitor the model cannot disable.

### [Alpine Linux Security Advisory: OpenSSH-server password authentication bypass](https://alpinelinux.org/posts/2026-11-05-openssh-password-authentication-bypass) — 7/10

If you run Alpine's default (non-PAM) openssh-server with password auth on, anyone who can reach port 22 can log in as root or any key-only account in a single connection, no password and no CVE to track yet.

Notes: The bug: sshd built without PAM hashes a login attempt with crypt() and compares it to the stored field; for accounts whose field is too short to hold a salt it borrows another account's salt. musl's crypt() returns the literal string '*' when the key exceeds 256 bytes, which is exactly what the shadow field holds for passwordless accounts, so the comparison matches and the login succeeds. · Exploit is deterministic: one connection, a single 257-to-1024-byte password, no retries. Preconditions are the name of an account whose password field is '*' (normal for key-only accounts) plus at least one local account with a $5$ or $6$ hash to supply the salt. · Affected: openssh-server (no PAM, Alpine default) or openssh-server-pam with UsePAM no, when PasswordAuthentication is yes (the OpenSSH default). root ships as root:* since ~3.16 but is shielded by PermitRootLogin prohibit-password unless an account can doas to root. Every checked release is affected: 3.16 through 3.24 and edge. · tiny-cloud images (qcow2/VHD/AMI) from 3.18.11 to 3.24.3 ship an 'alpine' user with field '*' and passwordless doas; safe at first boot but exploitable the moment any $6$ hash appears (admin console password, user-data hashed_passwd), yielding an alpine shell that doas-es to root. · Not affected: containers without sshd, PasswordAuthentication no, openssh-server-pam with UsePAM yes, accounts locked with '!' in /etc/shadow, machines with no $-style hash, and cloud-init images (which write PasswordAuthentication no). Fixed in OpenSSH 10.6p2 and backported packages (3.24: 10.3_p1-r2; 3.21: 9.9_p2-r1; down to 3.16: 9.0_p1-r6). · apk upgrade does not restart the running daemon: you must rc-service sshd restart afterward. No CVE assigned at time of writing; reported by Özgün Kültekin of Wakefield, fixed by OpenSSH's Damien Miller and Darren Tucker.
