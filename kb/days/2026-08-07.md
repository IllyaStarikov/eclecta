### [Don’t stop early: Case-folding source code at memory speed](https://github.blog/engineering/architecture-optimization/dont-stop-early-case-folding-source-code-at-memory-speed) — 7/10

If you write hot-loop text code, this shows a measured 15x jump on ASCII case-folding (3.1 to >45 GiB/s) that comes from deleting an early-exit branch so the compiler can vectorize, plus a 1776-byte Unicode table that folds in byte space without ever decoding a code point.

Notes: Scale motivation: GitHub's Blackbird code search indexes 180M+ repos and 480TB, case-folding every byte before ngram extraction and again per candidate match. Released as the Rust crate 'casefold'. · ASCII ladder on Apple M4 (5.7 KB buffer): naive branchy loop with early-exit break 3.1 GiB/s, 0 vector instrs; branchless body but keeping the break 2.6 GiB/s (slower, extra store traffic); dropping the break 7.6 GiB/s (partial vectorization); fully branchless test+write >45 GiB/s (full NEON, ~memory bandwidth). The data-dependent loop exit alone is what blocks vectorization; branchless is a pessimization in scalar code and only pays off as a vectorization enabler. · Folding is not lowercasing: folding is context-free and locale-independent (uses CaseFolding.txt statuses C and S), so if A matches B it does so symmetrically in any locale. The crate implements only simple 1-to-1 folds, skipping full folds (ss) and Turkic locale folds, matching ripgrep's choice for cross-tool consistency. · Unicode table is 1776 bytes (~9.6 bits/fold entry) covering Unicode 16.0's 1484 simple folds, versus ~11.6 KB naive, ~70 KB regex-syntax, ~7.3 KB Go, ~17 KB runtime HashMap. Layout: 64-code-point pages (folds touch 59 of ~1960), a 1-bit-per-page bitmap for a decode-free negative test straight from lead UTF-8 bytes, 238 packed runs (start/end/stride/delta, borrowed from Go's CaseRange), and an 8-wide SWAR compare over run keys. · The claimed-new part: fold as little-endian byte addition. Reading a character's UTF-8 bytes as a u32 and adding a per-run BYTE_DELTA yields the folded encoding directly, advancing by folded length, so length-changing folds (Kelvin U+212A to k; U+023A to a 3-byte char) work without decode/encode. Article claims ICU, Go, Rust regex, CPython, and glibc all decode first. Caveat: assumes well-formed shortest-form UTF-8; raw non-str bytes must be validated first. · Throughput vs real folders producing identical output (illustrative, auto-vectorization/SWAR/little-endian dependent): pure ASCII >45 GiB/s vs simd_normalizer 1.21 GiB/s and naive HashMap 213 MiB/s; CJK no-fold 2.95 GiB/s; worst-case all-folding Latin/Greek/Cyrillic 869 MiB/s (roughly tied with simd_normalizer's 922 MiB/s, about 2x slower than a simdutf decode/encode round-trip upper bound). Also >50% faster than the non-equivalent str::to_lowercase.
