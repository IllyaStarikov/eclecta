### [RefluXFS: A Linux Kernel Local Privilege Escalation to Root in XFS (CVE-2026-64600)](https://blog.qualys.com/vulnerabilities-threat-research/2026/07/22/refluxfs-a-linux-kernel-local-privilege-escalation-to-root-in-xfs-cve-2026-64600) — 8/10

If you run RHEL, Oracle Linux, Amazon Linux, or Fedora on their default XFS root, any local user can flip /etc/passwd and get root, and SELinux, containers, and kernel hardening do nothing to stop it.

Notes: CVE-2026-64600 is a race in XFS's copy-on-write path: two concurrent O_DIRECT writes to the same reflinked file collide when the kernel drops its inode lock to wait for transaction log space; the first writer re-checks the reference count using a stale physical block address, sees a count of one, assumes the block is private, and writes directly to the original file's block. O_DIRECT bypasses the page cache and lacks revalidation, so the overwrite lands on disk. · Preconditions: kernel 4.11+ (2017) without the patch, an XFS filesystem with reflink=1 in the superblock, and a directory writable by the unprivileged user alongside a root-owned config file or SUID-root binary. Qualys estimates over 16.4M systems affected (its own CSAM figure). · No practical mitigation short of patching and reboot. KASLR/SMEP/SMAP target memory, not block writes; kernel lockdown doesn't restrict O_DIRECT or FICLONE; SELinux Enforcing did not block the path in testing; seccomp profiles that allow write and ioctl (most do) don't help; container/user-namespace isolation operates above the allocation layer. On-disk changes survive reboot and leave no kernel log output. · Discovery method is the hook: Qualys TRU tasked Anthropic's Claude Mythos Preview (under Project Glasswing) to hunt for a Dirty COW-style race, iteratively narrowing prompts to memory-management and filesystem code; the model flagged the XFS race and generated a working PoC, which researchers then reproduced and verified. The model also drafted the advisory. Framed by Qualys as AI plus human oversight, not autonomous exploit generation. · PoC demonstrated on a default RHEL 10.2 install achieving passwordless root in seconds by modifying a protected system file. Confirmed affected: RHEL 8/9/10, CentOS Stream, Oracle Linux, Rocky, AlmaLinux, CloudLinux 8/9/10, Amazon Linux 2023 and Amazon Linux 2 AMIs from Dec 2022 on, Fedora Server 31+. Debian, Ubuntu, and SUSE are exposed only if an admin chose XFS with reflink=1. · Vendor-fixed kernels are available and being backported (RHSA/ELSA/ALSA/RLSA/FEDORA advisories listed). Full technical writeup and impact figures are Qualys-authored and self-reported; the linked advisory text and PoC video are the primary sources.

### [Concurrency vs. Throughput: why more parallelism can make databases slower](https://planetscale.com/blog/concurrency-vs-throughput-vitess-mysql) — 7/10

If your workload has hot rows or long-lived transactions, raising a connection or transaction pool cap to make errors disappear can invert throughput: this postmortem shows a MySQL shard recover by cutting its pool from 10,000 to ~1,000.

Notes: The 16-minute incident: a batch job held row locks for 15 minutes, forcing InnoDB to walk ever-longer MVCC version chains to build consistent snapshots for unrelated simple reads; reads that took milliseconds blew past a 90-second ceiling, apps retried in tight loops, and over 10,000 requests piled up until the buffer pool couldn't free memory. Errors peaked at 1,400/min as throughput fell from 15,000 to 1,500 qps. · The blocked reads were mostly not waiting on the locks themselves; the damage was snapshot reconstruction cost (coherency), which the article frames as the real failure mode versus focusing on 'lock contention.' · Migration from Cloud SQL (a queuing thread-pool that caps concurrent statements around 1,000 and makes clients wait) to Vitess vttablet's fail-fast transaction pool (waits a set time, then errors) exposed application code that had never handled pool-full errors. · The initial fix, raising the Vitess transaction pool to 10,000 (a number chosen to stop errors, not by sizing), removed backpressure and let InnoDB take on ~10,000 concurrent snapshot reads, worsening the coherency cost. · The framing uses Little's Law (N = X*W) and Gunther's Universal Scalability Law, X(N)=γN/(1+α(N−1)+βN(N−1)): the βN(N−1) coherency term quadruples when N doubles, and past N_max=√((1−α)/β) throughput reverses (retrograde scaling). Row locks map to α; snapshot rebuild cost maps to β. · Fix: cut the pool back to ~1,000 (the size the workload ran on for years) and queue with a longer bounded timeout instead of erroring. A later burst on a busier shard hit ~25,000 slot requests/s against ~1,000 slots with zero errors, flat ~60,000 qps, one rejected transaction all day, and fewer than 200 statements executing in MySQL at any instant (~3ms each by Little's Law). Vendor self-reported; scoped to contended/pessimistic-locking workloads, not universal.

### [FIPS 140-3 is not a security guarantee, and auditors know it](https://808bits.com/articles/fips-140-3-not-a-security-guarantee) — 7/10

If you are chasing FIPS 140-3 paper before the September 21, 2026 cutover, this argues the certificate covers only the module boundary, not key ceremonies, configuration drift, or side channels, which is where every cited incident actually happened.

Notes: Scope of a FIPS 140-3 validation: it attests that a specific firmware version in a specific configuration implements approved algorithms correctly, zeroizes keys, runs power-up self-tests, and (levels 2-4) resists tampering. It says nothing about the calling application, access control, key management, operators, or the key-generation ceremony. · Certified-and-broken examples: ROCA (2017) Infineon RSA key-gen flaw shipped since ~2012 under FIPS 140-2 and CC EAL5+ for five years, prompting Estonia to suspend ID cards; EUCLEAK (2024) non-constant-time ECDSA modular inversion went unnoticed 14 years across ~80 top-tier CC evaluations and hit YubiKey 5 FIPS and YubiHSM 2 FIPS (fix required hardware replacement); Dual_EC_DRBG stayed a NIST-approved, correctly-implemented DRBG for a decade until removed from SP 800-90A in 2014. · The 2019 YubiKey FIPS bug (firmware 4.4.2/4.4.4) was caused by FIPS requirements: leftover power-up self-test data left up to 80 predictable bits in 256-bit ECDSA nonces; the non-FIPS consumer key was unaffected, so the certified product was measurably weaker. FIPS mandates no constant-time or side-channel resistance at common levels. · The freeze problem: CMVP queue historically runs 12-18 months, so vendors either ship a fix and fall off the validated list or keep shipping known-vulnerable validated builds. Go 1.24 shipped a native pure-Go module (CMVP cert #5247, v1.0.0 frozen from Go 1.24) while v1.26.0 sits in Modules In Process, meaning a binary built today against the certified module runs crypto two major releases old. · Author's own Go 1.24/1.25.1 benchmark (GODEBUG=fips140 on vs off): ECDSA P-256 keygen 17µs to 110µs (the per-key pairwise consistency test), crypto/rand 32 bytes 85ns to 355ns (DRBG construction); ECDSA signing and AES-256-GCM unchanged. Approved mode also bans ChaCha20-Poly1305 without AES hardware and Argon2. · Digital assets are structurally incompatible: secp256k1, Keccak-256, and RIPEMD-160 are not FIPS-approved (AWS CloudHSM offers secp256k1/Ed25519 only on non-FIPS clusters), and BIP32 keys off the 12-character 'Bitcoin seed' constant (96 bits, below the 112-bit HMAC floor), so fips140=only panics on the first derivation. The 90%-run-it-off figure is a single unverified vendor sales-engineer anecdote.

### [Binding Drift in Multi-Step Tool-Augmented Agents](https://arxiv.org/abs/2607.18316) — 7/10

### [Assembly Hall of Shame](https://github.com/xoreaxeaxeax/asm-hall-of-shame) — 6/10

The same MMIO and microcode-assist tricks that stall a single instruction for 62 seconds are the raw material for timing side channels, SMM escapes, and denial-of-service against shared fabric, so knowing the worst-case latency floor of x86 instructions is defensive knowledge, not just a curiosity.

Notes: The top entry runs fxrstor64 to load 512 bytes of FPU/MMX/XMM state from a high-latency PCIe MMIO region on a Ryzen 7 5800H, while a fleet of hammer cores saturates the PCIe root complex with tight 4-byte non-posted reads; the timed instruction alone measures ~198,002,498,236 cycles (about 62 seconds).
