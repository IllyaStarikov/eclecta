### [Humans missed 1 in 3 threats approving AI agent commands across 40k game runs](https://scalex.dev/blog/ai-agent-permissions-stats) — 7/10

If you approve AI coding-agent commands under time pressure, this data says you will wave through roughly a third of real threats, and the exfiltration commands that actually leak credentials are the ones you miss most.

Notes: Dataset: a browser game where the player is the human-in-the-loop, analyzed across 40,000 runs and 409,000 approve/deny decisions. Mean threat-catch accuracy was 66.3%; 32.9% of sessions ended net-negative; 7% of players approved every prompt. · Miss rate scaled inversely with obviousness: obvious destructive commands (rm -rf /, chmod -R 777 /) missed 11.7%, persistent mutation 23.8%, exfiltration/code execution 33.4%, scope violations (cat ~/.aws/credentials) 35.0%. · The most-missed threat was 'npm run analyze' at 64.7%, whose package.json script piped bundle output to curl POST https://api.bundle.track/report; the malicious payload was visible in the agent history log yet approved anyway. Pooled across three npm-script traps the miss rate was 52.5% (n=9,482) versus 28.4% for other exfil-style attacks, roughly doubling success. · Benign commands were routinely blocked, generating fatigue-inducing noise: npm config set registry blocked 59%, rm -rf dist/ 45%, kill $(lsof -t -i:3000) 43%. cat ~/.zshrc split players (approved 45.9%) because its risk depends on whether the user stores secrets there, which the agent cannot see. · Author's caveat: this is a time-boxed game where ~34% of commands were threats and players knew they were being tested, unlike real workflows where threats are rare, so numbers are comparative signal, not a field measurement. Cites Anthropic's own note that permission fatigue lowers per-approval attention over time. · Structural argument (attributed to HN commenter dns_snek): approving individual commands is weak because npm run/build executes arbitrary shell from package.json, and the agent can edit package.json, build.js, or node_modules unprompted; suggested mitigations are sandboxing and separating credentials from env/shell profiles.

### [Cloudflare OS: an open platform for agents, apps, and work](https://blog.cloudflare.com/cloudflare-os) — 6/10

Notes: Diagnosis of the MCP gap: MCP restricts which tools an agent can call but does not record which underlying resources it observed, so agents can join data across systems and surface it through apps or outputs to people not cleared to see the source. · Mechanism: agents and apps start with access to nothing; access to a specific resource is granted as a typed capability binding (env.PROJECT), with the credential held by a service-specific Worker called a Gatekeeper that handles OAuth, enforces policy, masks fields, applies rate limits, and can require approval before side effects like merging a PR. · Observation log: every read is attached to the agent and its work; when another person opens the workspace or views outputs, Gatekeepers re-verify that person's access, and prior reads of sensitive data can block later writes, new collaborators, agent handoffs, or outbound requests. · Isolation: server code runs in Dynamic Workers (lightweight V8 isolates) with global outbound networking disabled; each app gets its own SQLite via a Durable Object Facet; the browser client talks to the server over Cap'n Web, Cloudflare's object-capability RPC, where the agent can invoke the same server methods a user can. · Two repos shipped: a Cloudflare OS core and an example deployment that consumes the core without patching; a shared app 'blueprint' copies code but not SQLite data, conversation history, credentials, or connected resources. · Every inference call routes through Cloudflare AI Gateway with per-person/team/workspace attribution, budgets, and rate limits; any model is allowed. Deployed internally to all Cloudflare staff since May 2026, with a companion post from CIO Sam Rhea.

### [Just One Function, 10x Faster? Reading a Rust Performance PR](https://greptime.com/blogs/2026-07-31-prom-read-conversion-optimization.html) — 6/10

A memory-only conversion function was burning a third of CPU on the Prometheus remote-read path; the fix is a reusable pattern (borrow from Arrow, don't rebuild per-row) that turned ~2M rows/sec into up to 34.8M rows/sec.

Notes: The hot function `recordbatches_to_timeseries` (in `src/servers/src/prom_store.rs`) converts columnar Arrow `RecordBatch` output into row-oriented Prometheus `TimeSeries`; the author's CPU profile (300k series, 4 concurrent reads, not reproduced by the writer) showed it at 36.2% of CPU, with dictionary materialization alone at 8.9%. · Root cause: cost scaled with row count R rather than series count S. The old code called `to_string()` per row (R·L string copies), allocated one `Vec<Label>` per row, and did a BTreeMap lookup per row, rebuilding the same label set repeatedly even though a typical remote read has few series with many points each. · Counterintuitive finding: dictionary-encoded columns (`Dictionary<UInt32,Utf8>`, the real PromQL layout) ran ~35% slower than plain Utf8 pre-fix, because `iter_column_as_string` didn't recognize dictionaries and expanded 3 shared strings back into 1000 owned Strings plus a per-row lookup. · The fix borrows `&str` straight from Arrow arrays via a `LabelValues` enum (one branch each for StringArray, LargeStringArray, StringViewArray, DictionaryArray), replaces the BTreeMap with a Vec plus a hash index, and adds a previous-series fast path exploiting that Mito's SeqScan sorts by primary key so samples of one series are mostly contiguous; copies drop from R·L to S·L, and a single final sort preserves the old BTreeMap output ordering. · Measured results (Apple M4 Max, macOS, 100 criterion samples, p<0.05): adjacent dictionary cases hit 12.4–16.5x (e.g. 1000×100: 55.6ms → 3.38ms); interleaved cases 4–5x; overall throughput 1.8–3.2M rows/sec → 9.6–34.8M rows/sec, no case slower. Ships in GreptimeDB v1.2.0-beta.1. · Caveats stated in the piece: the author didn't ship benchmark code (the writer rewrote it against the public entry point), the writer disputes the PR's 'silent skip' claim (arguing the old path actually panicked out of bounds), grouping is per-RecordBatch so series spanning batches aren't merged, and `hash_timeseries` uses DefaultHasher (SipHash-1-3, no stable-API guarantee) with ahash floated as a future experiment.
