### [PostgreSQL MVCC: tradeoffs compared to other engines](https://boringsql.com/posts/mvcc-bad-bad) — 7/10

Notes: Reproduced on a live PostgreSQL 19 beta2 instance: updating only the non-indexed last_seen column across 100k rows produced 7.1 WAL records/row on a table with 4 secondary indexes (69 MB WAL) versus 3.0/row on a bare primary-key table (36 MB), because indexes point at physical ctid and a moved row rewrites all of them. · HOT (Heap-Only Tuple) mitigation is opportunistic, not on-demand: fillfactor=70 got only 42% HOT updates on the first batch, rising to 66% (22 MB WAL) on a repeat after in-page pruning, and costs ~30% of table size in reserved space; author notes real OLTP tables reach 90%+ HOT. · A rolled-back 1M-row UPDATE still doubled the table to 178 MB with 47% dead tuples; abort took 0.124 ms because heap versioning does nothing on rollback, but the garbage remains for VACUUM. Undo engines (InnoDB, Oracle) instead reverse every row, and long UPDATEs can roll back slower than they ran. · Four questions frame every engine: where old versions live, chain direction (old-to-new vs new-to-old), index pointer type (physical vs logical), and who cleans up when. Postgres answers: in-table, old-to-new, physical ctid, background VACUUM. · The 'idle snapshot over lunch' failure recurs everywhere with different symptoms: Postgres holds back the database-wide xmin horizon and stops collecting garbage; Oracle kills readers with ORA-01555; InnoDB balloons undo; MongoDB/WiredTiger spills to a history store and smears latency; etcd and LSM engines (CockroachDB, Yugabyte) throw 'snapshot too old' / 'revision has been compacted'. · SQL Server (locking by default; versioning opt-in since 2005 via READ_COMMITTED_SNAPSHOT, versions stored in shared tempdb) added Accelerated Database Recovery in 2019 with a per-database persistent version store to get constant-time abort, the property Postgres has had by default. InnoDB uses 48-bit txn IDs and Oracle a 64-bit SCN, avoiding Postgres's 32-bit XID wraparound freezing (cited: Sentry's 2015 outage).
