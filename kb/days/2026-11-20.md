### [It's the Memory Latency, Stupid](https://pivotlake.io/blog/its-the-memory-latency-stupid) — 7/10

A GROUP BY that pegs a core at 100% can be spending half its cycles idling on DRAM, so the fix is cache locality, not more CPU, and perf counters will tell you which one you're hitting.

Notes: Baseline: naive hashtable GROUP BY on ClickBench 'hits' (99M rows, ~17M unique UserIDs), single core on an AMD EPYC 9124 Genoa bare-metal box, ran 3.9s first and 3.6s warm (page-cache hot). perf stat reported 50.1% backend_bound_memory (stalled on memory) and only 16.1% retiring micro-ops. · Rough latency budget the author cites: ~4-8 instructions/ns on a modern CPU vs 50-100ns per RAM access, so 400-800 instructions per DRAM load; L1 ~1ns and ~64KB, far caches up to a few hundred MB. · Radix partitioning fix: hash each key, use the top 12 bits (hash >> 52) to bucket rows into 4096 partitions first, then aggregate each small partition with its own HashMap so the working set fits in cache. More total work but less cold memory. · Measured result of the rewrite: warm time 2.7s, backend_bound_memory down to 23.5%, retiring up to 32.2%, and on-demand DRAM pulled dropped from 4.5GB to 1.5GB (ls_dmnd_fills_from_sys.dram_io_near * 64-byte cache lines). · Author's own Pivot engine (the vendor here) is claimed at 1848ms single-core (954MB DRAM) and 171.773ms across 16 cores on the same query; these are self-reported and the full Pivot algorithm is not shown. · Methodology caveat the author flags: used CherryServers bare metal, not AWS/GCP, because cloud VMs don't expose the DRAM-controller perf counters for security reasons; naive version is single-core because it can't parallelize.

### [Java sealed classes and exhaustive pattern matching](https://neilmadden.blog/2026/04/24/java-sealed-classes-and-exhaustive-pattern-matching) — 5/10

Notes: Sealed classes/interfaces (Java 17+) let the compiler verify a switch is exhaustive, so a default clause can be omitted when all permitted subtypes are covered. · Adding a new subtype breaks consumers: it causes a compile error in code that pattern-matches on the type, which under SemVer forces a major version bump if the type is public. · The compiler only catches the missing case when the consumer is recompiled; recompile the sealed type alone and the gap surfaces at runtime as java.lang.MatchException instead. · The JDK's own Javadoc flags this separate-compilation hazard, plus corner cases involving nulls in patterns. · Author hit this while reviewing JDK preview support for PEM-encoded cryptographic objects, which bakes a sealed interface into its public API and tells clients to pattern-match on it, setting up likely breakage if a case is ever added. · Recommended practice: use sealed types inside a component where everything recompiles together; avoid exposing them across module or library boundaries.
